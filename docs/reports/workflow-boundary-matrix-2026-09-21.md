# Codex 工作流边界冻结与分段验收

## 目的

冻结当前已同步的流程修改，明确四层职责，避免再次用 hook、Skill、Git guard 和 wrapper 互相重复判断。本文只记录边界和验收顺序，不代表整批生产发布已经完成。

## 最终职责

| 层 | 负责 | 不负责 |
|---|---|---|
| Agent / Skill | 根据项目上下文选择正常入口；理解“上预发/测试验证”默认包含集成、同步、构建、重启和检查；生成准确计划 | 不把某个固定命令或固定措辞当成唯一合法路径 |
| Codex PreToolUse hook | 拦截技术上危险或无法确认边界的动作：强推、删除、破坏性 reset、未知主机/目录/服务、生产缺少当前授权 | 不要求用户重复复制授权句；不判断用户是否“说得像授权”；不替 Agent 解析业务计划 |
| Git guard / 仓库保护 | 校验仓库级规则：快进关系、受保护分支、提交血缘、禁止删除/回退；master promotion 仍走项目正式入口 | 不替代 Codex hook；不把普通 pre/test 操作升级为生产审批 |
| wrapper / prodctl | 执行受控服务器写操作并留下服务器侧回执；生产部署、重启、迁移必须经过它 | 不负责理解自然语言；没有能力时必须明确失败，不能让 Agent 猜测或绕过 |

## 环境边界

- **pre/test**：用户明确要求“上预发/测试验证”后，默认使用项目公共 `pre`/`test` 分支完成集成、同步、必要构建、重启和验证。wrapper 可选；普通操作不重复询问。只有环境/目标冲突、共享环境被占用、破坏性操作或重大范围变化才暂停。
- **master**：用户明确要求合并或推送 `master` 时，Agent 应使用项目正式 promotion 入口；不能因为本地检查通过就直接绕过仓库 guard。
- **production**：必须使用 `prodctl` 和服务器 wrapper；当前轮明确授权绑定到具体计划、环境、版本和动作。生产整批发布必须分阶段推进，不能用单实例成功替代全量完成。

## 分段验收顺序

1. **pre**：新 session，用自然语言“上预发验证”，验证默认合并公共 `pre`、同步、构建、重启、健康检查；记录远端 SHA、服务版本、PID 和工作树状态。
2. **master**：在 pre 证据通过后，使用项目正式 promotion 入口合并/推送 `master`；验证仓库 guard 只校验血缘和快进，不再要求重复复制授权。
3. **production**：仅在前两段证据齐全后，按既定生产计划逐实例部署；每一步记录版本、服务状态、回滚点和观察窗口。若 wrapper 或服务器策略拒绝，停止修复入口，不改用 bypass 或原始 SSH。
